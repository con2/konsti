# client/CLAUDE.md

Guidance for working in the `client/` workspace (React 19 + Vite SPA). See the [root CLAUDE.md](../CLAUDE.md) for the project overview and cross-cutting conventions, and [shared/CLAUDE.md](../shared/CLAUDE.md) for the types/config/constants this workspace imports.

**No axios** — API calls go through a hand-rolled `fetch` wrapper (see below).

## Scripts

Run from the repo root as `yarn workspace client <script>`.

Each `build:*` script reads the matching `.env.*`; production goes through the root `yarn build-front:prod`, which builds and then copies `client/build` → `server/front`. Coverage runs at the root (`yarn coverage:vitest`), not here.

Note: `find-unused-translation-keys` is a **server** script (it scans `client/src`); run it via root `yarn find-unused-translation-keys`.

## Directory Layout (`client/src`)

- **`index.tsx`** — entry point: Sentry init, Redux `Provider`, styled-components `ThemeProvider`, then the lazily-loaded `App`.
- **`app/`** — `App.tsx` (initial data load + router wrapper), `AppRoutes.tsx` (all react-router routes), `lazyViews.ts` (the code-split views and their prefetch), `HistoryProvider.tsx` + `historyContext.ts` (tracks previous location for back buttons).
- **`views/`** — one folder per page/feature: `about`, `admin`, `admission-ticket`, `all-program-items`, `dashboard`, `event-log`, `group`, `helper`, `login`, `logout`, `my-program-items`, `profile`, `program-item`, `registration`. A view folder typically holds `*View.tsx`, its Redux `*Slice.ts`, `*Thunks.ts`, and a local `components/`.
- **`components/`** — shared UI primitives (Button, Input, Checkbox, Header, etc.) and `icons/` (FontAwesome). `componentStyles.ts` collects the style variant enums those primitives take as props (`ButtonStyle`, `HighlightStyle`, `InfoTextVariant`) — kept out of the `.tsx` files so Fast Refresh keeps working (see Build & Environment).
- **`services/`** — typed API call wrappers, one file per domain (`loginServices.ts`, `programItemsServices.ts`, `groupServices.ts`, …). Each just wraps `api.post/get/delete` with `shared/types/api/...` types.
- **`state/`** — only `loading/loadingSlice.ts` lives here; **the store itself and most slices do not** (see State Management below).
- **`locales/`** — `en.ts` and `fi.ts` translation objects.
- **`utils/`** — `store.ts` (Redux store), `hooks.ts` (typed Redux hooks), `api.ts` (fetch wrapper), `networkErrorPolicy.ts` (how failed requests are surfaced: background classification, reconnect grace period, probe, toast healing), `fetchWithTimeout.ts`, `dataPolling.ts` (the app-wide data refresh loop: interval, `online` and page-resume triggers, one load at a time), `pageLifecycle.ts` (`onPageResume`: page freeze/bfcache resume detection), `whenIdle.ts` (defers low-priority work to `requestIdleCallback`, timer fallback for Safari, which has never implemented it), `clock.ts` + `useTimeNow.ts` (the shared ticking clock and the hook that reads it, mocked time included), `i18n.ts` (i18next setup + locale type-check), `localStorage.ts`/`sessionStorage.ts` (zod-validated), `injectedScriptFilter.ts` (the Sentry filter options, shared with its tests - see Error Reporting), `getJWT.ts`, `checkUserGroup.ts`, etc.
- **`theme.ts`** — design tokens (colors, breakpoints, font sizes, popularity colors). **`globalStyle.ts`** — `createGlobalStyle`.
- **`markdown/`** — MDX content rendered as React components.
- **`test/`** — `setupTests.ts` (vitest/jsdom), `__mocks__/`, and dev-only UI helpers: `test-components/` (`TestTime` time selector, `TestGenerateSerial` registration-code button), `test-data/testDataServices.ts` (wrappers for the dev/test API endpoints). **`test/test-settings/testSettingsSlice.ts`** is the dev-only time-mock slice.
- **`types/`** — client-only types (`reduxTypes.ts`: `RootState`, `AppDispatch`, `AppThunk`; `styleTypes.ts`: `RgbColor`/`RgbaColor`/`Px`/`Opacity` template literal types for design token values; `errorTypes.ts`: `BackendError`/`BackendErrorType` — backend errors are stored in Redux as translation keys and translated at render time in `ErrorBar`, so removal matching survives language switches).

## State Management

Redux Toolkit, **thunk-based** (not RTK Query). The store is configured in **`client/src/utils/store.ts`** (not under `state/`). Slices are **colocated with their view** (`views/*/​*Slice.ts`), plus `state/loading/loadingSlice.ts` and `test/test-settings/testSettingsSlice.ts`. Async logic lives in sibling `*Thunks.ts` files.

- Access state with the typed hooks in **`client/src/utils/hooks.ts`**: `useAppSelector` / `useAppDispatch` (never the untyped react-redux hooks).
- Slice files export their reducer, actions, and memoized selectors (`createSelector`).
- Thunk result conventions: user-facing thunks return `Promise<SomeErrorMessage | undefined>` (truthy = failure, a translation key the caller renders); the background data-load thunks consumed by the polling loop return `Promise<boolean>` (truthy = success). Don't mix the two polarities up at call sites.
- Logout is handled by a `rootReducer` wrapper that resets most slices but preserves a few (e.g. `admin`, `allProgramItems`, `testSettings`).
- A Redux/Sentry enhancer scrubs large or private payloads (e.g. sign-up messages) before they reach Sentry.

## Services / API Layer

The API client is **`client/src/utils/api.ts`** — a `fetch` wrapper (no axios), exposing `api.post/get/delete`. It:

- prefixes requests with `config.client().apiServerUrl`,
- injects `Authorization: Bearer <jwt>` from `getJWT()` (JWT is read from localStorage),
- aborts after a 60s timeout (`AbortController`),
- on network/HTTP error, dispatches `addError(...)` into Redux (as a `BackendError` translation key, see `types/errorTypes.ts`) and returns an `ApiError`-shaped body — whether a failure toasts immediately (user-initiated requests) or gets the suppressed background handling (requests the app retries on its own, enumerated as method+endpoint pairs) is decided in `utils/networkErrorPolicy.ts`; see its header comment for the suppression mechanics,
- follows `301`/`302` JSON-body redirects via `location.href`.

Endpoint constants (`ApiEndpoint`, `ApiDevEndpoint`, `AuthEndpoint`) come from `shared/constants/apiEndpoints.ts`; request/response types from `shared/types/api/...`. To add an API call: add a function in the relevant `services/*.ts`, type it with the shared request/response types, and call it from a thunk that dispatches the result.

## Styling

styled-components only (no CSS modules, no component library). Pull tokens from the theme via props: `(props) => props.theme.breakpointPhone`. Breakpoints come in pairs - `max-width` uses `breakpointPhone`/`breakpointDesktop`, `min-width` uses the `…Min` variants, which sit 0.02px above so a viewport exactly on the breakpoint (iPad portrait is 768px, landscape 1024px) belongs to the smaller side only: `@media (max-width: ${(props) => props.theme.breakpointPhone})` and `@media (min-width: ${(props) => props.theme.breakpointPhoneMin})`. Global resets in `globalStyle.ts`. Stylelint (with the a11y plugin) lints the CSS-in-JS — run `yarn workspace client stylelint`.

**Always source colors from `client/src/theme.ts`** — never hard-code color values (hex/rgb) in components. Stylelint enforces this (`color-no-hex`, `color-named`, and `function-disallowed-list` for the color functions in the root `.stylelintrc.ts`), so a literal color in a styled template fails `yarn lint`; the `transparent` and `currentColor` keywords are still allowed. Use `props.theme.<token>` in styled templates; in a context without props (e.g. module-level `keyframes`), `import { theme } from "client/theme"` and reference `theme.<token>` directly. Add a new token to `theme.ts` rather than inlining a one-off color.

**`theme.ts` itself is two layers: color constants first, then context tokens that reference them.** The top of the file defines the raw values — named neutrals (`offWhite`, `white`, `black`, …) and palettes (`green.primary`, `gray.lightest`, …) — and every entry in the exported `theme` object points at one of those names (`backgroundDisabled: gray.light`), never at an inline `rgb(...)` string. Adding a color means adding it to a palette at the top and referencing it below, so the same shade is defined once and shared by every context that uses it - prefer a new shade in the palette its hue belongs to over a one-off standalone constant, and prefer an existing shade over a near-duplicate of one. Composed values follow the same rule: shadows interpolate a color constant (via `addOpacity` for translucency) instead of embedding `rgba(...)` literals. Token values are checked against the `styleTypes.ts` types where they are defined - colors through the annotated constants (`const white: RgbColor = …`), sizes through `satisfies` on the literal - so a malformed color or a value in the wrong unit is a compile error at the definition. Use one of those two forms, never an `as` assertion, which validates nothing. Note `satisfies` widens the property to `string` in the exported `Theme` type, so only the color tokens carry their type through to consumers; the shadow tokens are composed strings and are unchecked.

**Don't export styled-components.** A module's public export should be a React component with explicit props that renders its styled elements; `styled` definitions stay module-private. Exporting a bare styled-component leaks styling as API and usually signals a composition problem — wrap it in a component instead (see `ProgramItemStatusMessage`). Restyling an imported component locally with `styled(Component)` is fine.

**Prefer component logic over stateful CSS.** When layout depends on application state, express it in the render logic, not in CSS selectors. A component with nothing to show returns `null` instead of rendering an empty element hidden with `:empty`/`display: none`, and spacing that depends on what renders around an element comes from explicit margins on the components involved, not from positional selectors like `:last-child` (a `display: none` element still matches structural pseudo-classes, and such CSS silently drifts from the render logic it mirrors).

## Internationalization

i18next, English + Finnish. Locale files: `client/src/locales/{en,fi}.ts` (deeply nested `as const` objects). `client/src/utils/i18n.ts` has an `expectLocalesToMatch` type-level check — if EN and FI don't have identical key shapes, type-check fails. The same `NestedKeyOf` machinery makes `t("...")` calls type-checked at the call site (missing keys are TS errors).

**Translation keys are client-only.** Server/shared/playwright code must never reference translation keys (the i18next instance only exists in the client). The unused-keys detector only scans `client/src` and treats any apparent reference outside as a bug to investigate, not a use.

**Dynamic key patterns to know about:**

- Template-built keys: `t(\`programType.${type}\`)`, `t(\`attendeeTypePlural.${getAttendeeType(programType)}\`)`. The detector tracks these as wildcard skeletons (`programType.\*`).
- Keys held as TS enum values: `enum PostLotterySignupErrorMessage { UNKNOWN = "signupError.generic", ... }`. Easy to miss with a naive grep for `t("…")`. The detector handles this by matching any string literal against the known key set.

`yarn find-unused-translation-keys` reports unused keys (exits 1 if any). Wired into `yarn lint` and the CI lint job. The event-log views (`views/event-log/`) render the program-item cancellation actions described in [server/CLAUDE.md](../server/CLAUDE.md) via `eventLogActions.*` keys.

## Build & Environment

- **Vite** (`client/vite.config.ts`): outputs to `client/build/` with sourcemaps; build target derived from `.browserslistrc`; plugins for MDX, SVGR (SVG→React), React, static copy, and gzip/brotli compression; `tsconfigPaths` resolves the `client`/`shared` aliases; dev server bound to `127.0.0.1:8000`.
- **Fast Refresh is lint-enforced:** `eslint-plugin-react-refresh`'s `vite` config runs over `client/**` in the root `eslint.config.ts`. A module that exports a component plus anything else loses Fast Refresh and falls back to a full page reload, so enums, hooks, helpers and standalone styled-components shared between modules live in their own file (`components/componentStyles.ts`, `app/historyContext.ts`, …) rather than beside the component that first needed them. The `vite` variant allows constant exports, which `@vitejs/plugin-react` handles.
- **Chunking** (`build.rolldownOptions.output.codeSplitting`): dependencies are grouped out of the app's own chunks into `react` (react/react-dom/scheduler), `sentry` (`@sentry/*`) and `vendor` (the rest of `node_modules`), so their content hashes survive an app-only deploy and a returning client re-downloads app code alone. Use `codeSplitting` — `advancedChunks` is the deprecated spelling of the same option. Group `test` regexes match module ids, which are Windows paths locally, so write separators as `[\\/]`.
- **Boot preloads** (`client/src/vitePlugins/preloadBootChunksPlugin.ts`): Vite emits `<link rel="modulepreload">` only for the entry's **static** import graph, so chunks behind a dynamic import don't start downloading until the entry has downloaded, instantiated its dependencies and run. The plugin names modules that are needed on every load anyway (currently `app/App.tsx`) and preloads their chunks, minus whatever Vite already covers. It fails the build if a named module no longer resolves to a chunk, so a rename can't silently drop the hint. Only list always-needed modules here — a genuinely deferred view should keep discovering its chunk at navigation time.
- **Sentry stamp assertion** (`client/src/vitePlugins/assertSentryStampPlugin.ts`): fails the build if any emitted chunk lacks the module-metadata key the Sentry plugin injects. It judges the **finished bundle** in `generateBundle`, so the chunks it names are the ones on disk — a chunk still being rendered carries a hash placeholder (`App-!~{003}~.js`) that matches no file anyone can go and look at — and a chunk another plugin has since emptied, filled or deleted is taken as it now stands. Exactly one thing is carried over from `renderChunk`: an HTML-facade chunk holding nothing but re-exports, which the Sentry plugin skips using a line-anchored test that reads minified code as ordinary code, so it cannot be re-asked later. `enforce: "post"` puts its hooks after other plugins'; **array position decides nothing here**, since Vite orders by `enforce` first. See Error Reporting for why it is load-bearing.
- **React Compiler is ON**, wired as `@rolldown/plugin-babel` running the plugin's `reactCompilerPreset`. It has to go through Babel: `@vitejs/plugin-react` v6 transforms JSX with Oxc and takes **no** `babel` option of its own, so the `babel: { plugins: [...] }` that used to enable the compiler was silently ignored from the Vite 8 upgrade onwards and the codebase spent months un-memoized. The coverage build (`COVERAGE=true`) leaves it out: the compiler's rewrites move the statements istanbul instrumented out from under the positions it recorded. `babel-plugin-react-compiler` pins `@babel/core` to 7.x — it depends on `@babel/types@^7`, and Babel 8 would give it a second copy.

  Enabling it meant fixing what it exposed, none of which `yarn lint`, `yarn type-check` or the unit suite could see:
  - **`useTimeNow`** used to read the current time while rendering. The compiler had nothing to key that on, so it cached the instant behind the first-render sentinel and froze the clock at whatever each component mounted with. The mocked-time branch keys on `testTime` and stayed correct, so the **entire Playwright suite passed** while real users saw a frozen clock. It now reads a shared ticking store (`utils/clock.ts`) through `useSyncExternalStore`, which also makes the value referentially stable between ticks, so it can be listed as a dependency like anything else. That store is unit-tested (`utils/clock.test.ts`) precisely because the E2E suite runs on mocked time and cannot see this class of bug.
  - **`AllProgramItemsList`** is the one deliberate opt-out (`"use no memo"`): `useWindowVirtualizer` returns a render-stable instance whose measurements mutate inside it, so the row offsets and total size read from it during render are external mutable state. Memoized, rows keep the offsets they first rendered with and a sign-up form's Confirm button ends up underneath the next row (caught by `lotterySignup` specs 209/300).
  - **A ref read during render** makes the compiler decline the component outright — `HistoryProvider` and `EventLog` both did. Both hold the value in state now; in `HistoryProvider` that also fixed a real bug, where the current location promoted itself to being its own predecessor on any re-render that wasn't a navigation, while `EventLog`'s mount snapshot behaves the same either way.
  - **Only a plain `try`/`catch` is supported.** A `finally` is declined (`Handle TryStatement with a finalizer`) and so is a catch-less `try`, and either one declines the entire enclosing function. The polling loop needs its `finally`, so it moved out of `App.tsx` into `utils/dataPolling.ts`, where the compiler doesn't look; the Kompassi redirect handler dropped its `finally` for a `catch` plus a reset after the block, and stayed where it was.
  - **Mutating a `useState` array in place** and passing the same reference back (`AdminActionCard`) — an immutable update now.

  **Suppressing `react-hooks/exhaustive-deps` or `react-hooks/rules-of-hooks` makes the compiler silently skip the whole surrounding component**, with nothing in the build output saying so (`AllProgramItemsView` compiled to zero memo slots). Worse, the compiler only recognizes `eslint-disable` and `eslint-disable-next-line`, so an `eslint-disable-line` suppresses the rule while the component still gets compiled. `@eslint-community/eslint-comments/no-restricted-disable` in the root `eslint.config.ts` now rejects both rules; a component that genuinely can't be compiled has to say so with `"use no memo"`. Only those two are in the compiler's default suppression list, so the other `react-hooks` rules can still be disabled without this effect.

  **It costs about 11% of the app's JavaScript** — 289 → 322 kB gzipped, measured with `build:ci` against a build with only the Babel plugin line disabled. The cost lands entirely on component-dense chunks: `App` 18.4 → 33.3 kB (+81%) and `PasswordChangeForm` 17.5 → 27.9 kB (+60%), while `react`/`vendor`/`sentry`/`index` come out byte-identical. `App` is on the critical path of every page load via the boot preloads, so that is the number to watch; there is no knob to reduce it.

  The clock the whole app reads (`utils/clock.ts`) is worth understanding before touching anything time-dependent: it ticks on **wall-clock minute boundaries**, not on a page-load-relative phase, so a sign-up window opens at the same instant for every client rather than up to a minute apart depending on when each one loaded - which for first-come-first-served sign-ups decides who gets a spot. It also resyncs on page resume, because a frozen page runs no timers and would otherwise render freshly polled data against a pre-sleep instant. A consequence worth knowing: the program list re-filters as the clock advances, so an item whose direct sign-up has ended leaves the "Last started and upcoming" view within a minute instead of lingering until the polled data happens to change.

  Its Rules-of-React lint checks are **not** the deprecated standalone `eslint-plugin-react-compiler` — they ship inside `eslint-plugin-react-hooks` (v7) `recommended` (`react-hooks/purity`, `immutability`, `preserve-manual-memoization`, etc.), already enabled — and they caught none of the above. To find out what the compiler itself thinks of the code, run it over `client/src` with a `logger` and read the `CompileError`/`CompileSkip` events; that sweep is what turned each of these up.

- **`client/vite.config.ts` is type-checked by the root `tsconfig.json`** (not the client one, whose browser-era `lib` rejects the Node APIs `scripts/` uses), so a dead config option like the ignored `babel` key fails `yarn type-check` instead of only showing up in an editor. **The Vite plugins themselves live in `client/src/vitePlugins/`**, which the client project's `src/**/*` glob already covers. Put one at the client root instead and it lands outside every TypeScript project, so it needs its own `client/tsconfig.json` `include` entry or ESLint fails it with "was not found by the project service" — which is why they moved. Being build-time code the browser never runs, that directory is excluded from the coverage globs.
- **Sentry source maps** (`@sentry/vite-plugin`, which declares `enforce: "pre"`, so Vite hoists it regardless of where it sits in the list): for `production`/`staging` builds — and `development` builds when `enableSentryInDev` is set — it injects debug IDs into the bundle, uploads the maps to the matching `konsti-frontend-{prod,staging,dev}` project, then deletes the `.map` files so they aren't shipped. The plugin runs on every `vite build` (and only there — `command === "build"`, since its stamping lives in `renderChunk`, which the dev server never reaches), but its **upload** only runs when a `SENTRY_AUTH_TOKEN` is available — a build secret in the Docker build via `deploy.yml`, or the gitignored `client/.env.sentry-build-plugin` file for local builds (copy `.env.sentry-build-plugin.sample`). That file is in `.dockerignore` as well as `.gitignore`, and needs to stay in both: the `COPY client ./client/` in the `Dockerfile` would otherwise bake a developer's personal token into an image layer and upload source maps to the real project from a laptop. **Every developer-local env file needs both**, not just this one - `.env.local` and `.env.*.local` both outrank the committed `.env.<mode>` in Vite's `loadEnv`, so a `PORT_OFFSET` pinned in one per the README would bake an API URL into the image pointing at a port nothing in the container listens on. `.env.local` needs its own `.dockerignore` line: the `.env.*.local` pattern is longer than that filename and cannot match it. Without one (`enableSentryUpload` false) the build proceeds with `sourcemaps.disable` on and `release.create`/`inject`/`finalize` off, so it neither uploads nor stamps a release that has no artifacts — it still stamps the `applicationKey` every build needs (see Error Reporting). `build.sourcemap` follows the same gate, so a build with no upload generates no maps at all, rather than generating them for the plugin's cleanup to delete. **It is deliberately not `silent`:** that flag mutes `logger.error` as well as warnings, and the state it would mute is exactly the one a production build falls into when its Sentry secret goes missing — `Dockerfile` turns an absent secret into an empty string, so silence there would ship an unsymbolicated bundle with nothing saying so. That is not left to the plugin, though: its own "no auth token" warning sits behind the source map **upload**, which a token-less build turns off for the same reason, so it never fires. `vite.config.ts` warns for itself instead whenever a `production` or `staging` build has no token. Debug IDs mean symbolication works without a `release` in `init()`. The deployed bundle is built (and uploaded from) inside the `Dockerfile` so the served files carry the IDs that match the uploaded maps — the git SHA is passed in as the `APP_VERSION` build-arg because the Docker context has no `.git`. Because the upload runs during the image **build** (before the `deploy` job in `deploy.yml`), a _failed_ deploy still leaves the new release's maps uploaded — this is harmless: debug IDs are content-addressed, so the unused maps are never consulted while the still-live previous bundle keeps symbolicating against its own maps. The only residue is a finalized frontend release in Sentry for a SHA that never went live (no events attach to it). Uploading at build time is Sentry's recommended pattern for exactly this reason.
- **Env files** are selected by build `--mode`: `.env.development`, `.env.staging`, `.env.production`, `.env.ci`, `.env.kube-dev`. Vite's `define` exposes config as `process.env.SETTINGS`, `process.env.API_SERVER_URL`, `process.env.SHOW_TEST_VALUES`, `process.env.DATA_UPDATE_INTERVAL`, and `process.env.APP_BUILD_TIME` (seconds since the epoch at which the image was built, from the `APP_BUILD_TIME` build-arg; development/ci builds fall back to `0` so E2E can drive the update banner by faking a later time; these are **not** `VITE_`-prefixed) — they feed `config.client()` in `shared/config`. There is deliberately **no `IS_BUILD` define**: the one thing that needed it asks the running bundle instead (see Error Reporting). `APP_VERSION` is read by the Sentry plugin for the release name but is **not** exposed to the bundle, and no longer appears in the settings response either: nothing in the client handles a git SHA.
- **Browser support:** `.browserslistrc` targets browsers from roughly the last 5 years; `eslint-plugin-compat` and `stylelint-no-unsupported-browser-features` enforce it.

## Error Reporting

`Sentry.init()` in `index.tsx` has three filters available, in decreasing order of preference for a new exclusion: `ignoreErrors` (message substrings), `denyUrls` (script URL patterns), and `thirdPartyErrorFilterIntegration`, which drops on the shape of the stack. Only the last carries any rules today.

Most of what reaches the production project is not app code at all: in-app browsers (Instagram, Facebook, Brave) and mobile browsers' own autofill and translate features inject scripts into every page, and their errors are reported as the page's own. **`ignoreErrors` and `denyUrls` are both gone**, on the bet that the stack-shape filter now covers what the six accumulated message patterns and the one URL pattern used to. Two cases are known _not_ to be covered, so recognise them if they return: the Outlook link-scanner's `"Non-Error promise rejection captured with value: Object Not Found Matching Id:"` arrives with **no stacktrace at all**, which the filter leaves alone by design; and the in-app-browser bridge error (`"Error invoking post…"`) survives whenever the SDK's own wrapper frame sits at index 0 without `pre_context`, because `isSentryInternalFrame` then declines to strip it and its stamp makes the event read as first-party. **Add an entry back whenever a message or script URL identifies the source** — that is cheaper and more precise than widening the stack-shape filter — and give each one a comment naming the browser it came from. Keep the patterns short enough to survive a variant: the bridge one wants `"Error invoking post"`, not the full `"…: Method not found"`, because the same script also throws `postEvent` and `postMessage` forms.

**`thirdPartyErrorFilterIntegration` covers what those cannot:** injected code whose message is indistinguishable from an app error (`Maximum call stack size exceeded`, say), where only the stack tells them apart. `@sentry/vite-plugin` stamps every emitted chunk with `applicationKey` (`config.sentry().applicationKey`, the same value `filterKeys` reads, so the two cannot drift), and the integration drops an event whose frames all lack that stamp — injected code carries none. **Whether it drops or only tags is `config.sentry().dropInjectedScriptErrors`.** Setting it to `false` switches the integration to `apply-tag-if-exclusively-contains-third-party-frames`, which keeps every event and marks the matching ones `third_party_code: true` — the reversible way to count what the filter is removing before trusting it, at the cost of that noise still arriving through the tunnel. The tests stay green either way: they spread the app's own options and override the behaviour each one is pinning. **Its options live in `utils/injectedScriptFilter.ts`** rather than inline at `init()`, so `utils/sentry.test.ts` exercises the options the app actually uses instead of a copy of them; `shared/config/sentryConfig.ts` spells the metadata prefix once, as `sentryApplicationKeyPrefix`. It identifies app code **positively** rather than guessing from filenames, so it also catches a genuine third-party `.js`, and it needs no `moduleMetadataIntegration` alongside it, registering `applyFrameMetadata` itself. It runs with `ignoreSentryInternalFrames`, because the SDK wraps timers and DOM handlers and that wrapper sits in a stamped chunk — without it an injected script error keeps a first-party frame and survives. That option is marked experimental and cuts both ways: in a minified bundle it recognizes the wrapper as "no source context and a name of one or two characters", which an app frame can also match, and it only applies to single-exception events, so a wrapped error arriving as a cause chain keeps its wrapper frame regardless.

**It fails closed, and that is the price of dropping rather than tagging.** The integration discards frames it cannot place (no `filename`, or no line/column/address) and then asks whether _every_ remaining frame is third-party — which an empty set satisfies vacuously. So an error whose frames all lack a filename, or whose `stacktrace.frames` is empty, is dropped even though nothing identified it as injected. An exception carrying no `stacktrace` key at all is kept, which is what keeps a thrown non-Error reporting. `utils/sentry.test.ts` pins all of these against the real SDK; with `sendClientReports: false` there is no telemetry for what gets dropped, so those tests are the only place this behaviour is visible. They also drive the **metadata join** itself: the build writes a stack into a global at chunk load and the SDK matches event frames to it by filename, and if that match ever breaks every frame reads as third-party and the whole stream is discarded — which the build-time check cannot see, since it only proves the string is in the file.

**An error the app caught is often not the app's to report.** A rejected dynamic import throws with the document URL as its only frame: placeable, so the filter keeps considering it, but unstamped, so the event reads as exclusively third-party and is dropped. `utils/lazyWithRetry.ts` therefore reports a **new** `Error` built in app code, whose stack is topped by stamped frames, and rethrows the caught one for the error boundary — handing the caught error to `captureException` instead would compile, lint and test clean while silently losing every chunk-load failure, which is the only signal that a deploy left users on stale chunks. The same applies anywhere else a caught error originates outside the app's own bundles.

**It is left out unless the running bundle is actually stamped**, which `isBundleStamped()` asks of `globalThis._sentryModuleMetadata`. Stamping happens in `renderChunk`, which `vite serve` never runs, so a dev session carries no stamps and every frame would read as third-party — the filter would discard everything. This was once a `process.env.IS_BUILD` define read as `config.client().isBuild`, with its own plugin asserting the two spellings had not drifted; observing the stamp retired the proxy, the define and that plugin, and it fails in the safer direction, because a bundle that somehow lost its stamps now leaves the filter off rather than discarding everything. Three things make it sound. The stamp is an IIFE **prepended to every chunk**, so the store is populated before `init()` runs in the entry chunk's own body. The check asks for **this app's own key**, not merely for metadata existing, so a dependency stamped with someone else's key cannot answer for it. And it reads that global directly because the SDK does the same and exports no reader for it — `getFilenameToMetadataMap` is not re-exported by `@sentry/react`. **Runtime code must build the key from `sentryApplicationKeyPrefix` and never spell it whole:** the quoted key alongside `_sentryModuleMetadata` is exactly what the build-time check reads as proof of a stamp, so spelling it out would let a chunk vouch for itself.

**The stamping is not gated on `SENTRY_AUTH_TOKEN`.** In `@sentry/bundler-plugin-core` only the plugin's own `disable` option suppresses it, while `authToken`/`org`/`project` gate release creation and source map upload, each of which warns and skips. So `vite.config.ts` gates only the network work on `enableSentryUpload` — a token-less build still ships the stamps, and still deletes its `.map` files, which are emitted by `build.sourcemap` and would otherwise be served publicly. Note `release.create` covers neither `finalize` nor `setCommits`; both reach Sentry on their own, so `finalize` follows the gate and `setCommits` is off everywhere (the Docker context has no `.git` for commit detection to read). Cost is roughly 520 bytes raw / 230 gzipped per chunk (one IIFE per chunk, not per module).

**`assertSentryStampPlugin.ts` is what holds that in place**, and it is load-bearing: an unstamped bundle would discard **every** error, and `sendClientReports` is deliberately `false` (the tunnel carries error events only), so nothing at runtime would say so — the project would just go quiet, which is indistinguishable from a quiet week. It fails the build instead, naming the chunks that lack the key. Three things about it are deliberate: it matches the key **quoted on both sides**, because the SDK compares for equality and an unanchored match would accept a longer key that merely starts the same — accepting any of the three quote characters, since which one survives minification is the minifier's preference and not a contract. A chunk must also contain `_sentryModuleMetadata`, so the key alone is not taken as proof: a chunk that merely imported the constant naming it would otherwise satisfy a check whose whole point is that its failure is invisible at runtime. And it requires the key from **every non-empty JavaScript chunk**, predicting nothing about what the stamper skips, so it also fails when **no** chunk had to carry the key and cannot pass by checking nothing. That last part is a deliberate trade. `@sentry/rollup-plugin` declines exactly one kind of chunk an app would otherwise expect stamped — an HTML facade holding nothing but imports, which [needs multiple entry points](https://github.com/getsentry/sentry-javascript-bundler-plugins/issues/829) and which this single-`index.html` SPA has never produced (21 of 21 chunks carry the key). Predicting that skip meant importing `isJsFile`/`shouldSkipCodeInjection` from `@sentry/bundler-plugin-core`, as a direct devDependency held in version lockstep by a Yarn constraint, and asking the whitespace-sensitive one during `renderChunk` because its import-only test is line-anchored and reads minified code as ordinary code. None of that is here any more: **the check imports nothing from Sentry**, and a build that ever grows a facade chunk fails loudly naming it rather than being excused by a prediction. **The verdict is reached on the finished bundle**, in `generateBundle`, so the names it reports are the ones on disk and a chunk another plugin has since emptied, filled or deleted is judged as it now stands. Do not reintroduce a token gate around `sentryVitePlugin`, and do not weaken that assertion.

**Exercising any of this locally takes a build, not the dev server.** `vite serve` stamps nothing, so `isBundleStamped()` is false and a dev-server session says nothing about the filter: build instead (`yarn build-front:dev`) and let the server serve `server/front` on port 5000. Sending at all additionally needs `config.sentry().enableSentryInDev`, which gates the client DSN (`konsti-frontend-dev`) and the server's (`konsti-backend-dev`) together — revert it **and rebuild** afterwards, or the bundle left in `server/front` keeps reporting. The Admin view's **Sentry testing** buttons are the triggers: _Client test_ throws a `TypeError` inside a click handler (so it also exercises `ignoreSentryInternalFrames`, the SDK's wrapper frame being the outermost one), and _Backend test_ calls the admin-only `GET /api/sentry-test`. One trap when checking the result: `getDsn()` reads the flag at **runtime**, so both DSN strings are present in every bundle whatever the flag says — grepping a bundle for a DSN proves nothing, so check the shipped `enableSentryInDev` value instead.

## Testing

Vitest with the jsdom environment; setup in `client/src/test/setupTests.ts` (initializes i18next with EN). Coverage via Istanbul. There are few committed unit tests today — add them alongside the component/view under test.

**Don't write component (rendering) tests** — there is no testing-library dependency, and rendered UI behavior is covered by the Playwright E2E suite instead (see [playwright/CLAUDE.md](../playwright/CLAUDE.md)). Keep client vitest tests to pure functions/utils/reducers (e.g. `programItemUtils.test.ts`, `adminSlice.test.ts`); when a fix changes what a component renders, add or extend an E2E spec.

For the combined-coverage flow (`yarn coverage`, see the root CLAUDE.md), starting the dev server with `COVERAGE=true` serves istanbul-instrumented code (`vite-plugin-istanbul`) and disables the react-compiler babel plugin (its rewrites break the coverage source positions). `client/src/vitePlugins/coverageCollectorPlugin.ts` then harvests the browser's `window.__coverage__` server-side: it injects a flush script into `index.html` and receives the data on a `/__coverage__` dev-server middleware, so the Playwright suite needs no coverage hooks of its own.

## Other Notes

- **Forms:** react-hook-form (`useForm`, `register`, `handleSubmit`); validation messages come from i18next keys.
- **Lazy loading:** `utils/lazyWithRetry.ts` wraps `React.lazy` to retry failed dynamic imports. `index.tsx` loads `App` through it, and **`app/lazyViews.ts`** owns the route-level splits — the About tabs (`AboutView`/`FaqView`/`InstructionsView`) and the `AdminView`/`HelperView` staff tools — so the code-splitting mechanics stay out of `AppRoutes.tsx`, which just renders them. `components/PrivacyNoticeText.tsx` separately defers the privacy notice Markdown, so the standalone `/about/privacy` route (`views/about/PrivacyNoticeView.tsx`, deliberately not an About tab - a fourth tab wraps to two rows on a narrow phone in Finnish) is **not** in `lazyViews.ts` — its content is already split one level down, and an eager view can't fall out of step with the prefetch list. The same chunk backs the registration accordion (`components/PrivacyNotice.tsx`), where it loads only once the accordion is opened. The route-level `Suspense` boundary sits around `<AppRoutes />` in `App.tsx`, not at the root, so a view loads with the header and sticky bars still on screen. Split content-heavy or role-restricted views; leave the critical path (login form, program list) eager. `lazyViews.ts` also exports `prefetchLazyViews(userGroup)`, which `App.tsx` runs through `whenIdle` once the first data load has finished — the About tabs for everyone, the staff tools only for the roles that can open them. It re-runs when the role changes, so signing in as staff warms the chunks that just became reachable. Keep that list and the `lazyWithRetry` definitions in step: a view split without a matching prefetch entry silently keeps its loading spinner.
- **App update notification:** `components/AppUpdateBanner.tsx` prompts a reload when the build time the server reports in the polled settings response is **strictly newer** than this bundle's own (`config.client().appBuildTime`, from the `APP_BUILD_TIME` build-arg). Comparing order rather than identity is what distinguishes a server that has moved on from one that simply hasn't rolled yet: mid-rollout a page served by an already-updated instance keeps polling instances still on the old build, and a difference-based check would tell it to update to the version it is already running. The build-arg is stamped at **deploy** time, not commit time, so a rollback — an older commit, but the newest deployment — still reaches clients. A build is accepted only after polls have reported it unchanged for half a poll interval (`updateServerAppBuildTime` in `adminSlice`), which additionally guards against acting on a single anomalous response. It also reloads transparently on the first route navigation after detection, at most once per build (sessionStorage guard prevents reload loops) — keyed on the build rather than the revision, so redeploying the same code still gets its own reload. The build time is the only deploy identifier the client sees; it drives detection, the dismissal and that guard alike. Never shows in local dev on its own because the server reports no build time there; the E2E spec fakes one to drive it.
- **Local/session storage:** zod-validated in `utils/localStorage.ts` / `utils/sessionStorage.ts`; session state (incl. JWT) lives under the event-prefixed state key. All Konsti storage keys carry the `konsti-<eventName>-<eventYear>` prefix from `shared/constants/browserStorage.ts` (also used by the Playwright login helper), and `utils/resetStaleEventStorage.ts` (called in `index.tsx`) removes previous events' keys on page load — so old events' data is never read and needs no migration. Prefix any new storage key the same way. Within one event, don't change persisted shapes: the JWT shares the state object with saved preferences, and a strict parse failure clears the session and logs the user out.
- **Dev tooling:** axe-core (a11y) and why-did-you-render run in dev when enabled in client config.
- **User-group checks:** `utils/checkUserGroup.ts` (`isUser`/`isAdmin`/`isAdminOrHelper`) gate views and UI.
- **Local login lives at `/admin/login`.** `/login` renders only what the `loginProvider` **setting** permits, so for a Kompassi-only event the username/password form is not on that page at all. `/admin/login` reaches it regardless, which is how the seeded accounts (`admin:test` and the rest, see the root CLAUDE.md) sign in locally.
