# browserstack/CLAUDE.md

Real-device checks through BrowserStack Automate, run in CI and by hand, for behaviour the Playwright suite cannot reach. See the [root CLAUDE.md](../CLAUDE.md) for the project overview and [playwright/CLAUDE.md](../playwright/CLAUDE.md) for the automated E2E suite.

**Why this exists.** Playwright's WebKit build is not Safari, and nothing automated can turn a phone's screen off, background Safari, or restore a page from the bfcache. The client's page-resume handling (`client/src/utils/pageLifecycle.ts`, consumed by the data poll in `dataPolling.ts`, the clock and the network-error policy) depends on exactly those events, so it is verified here on real iPhones before changes to it are merged. Playwright on BrowserStack would not help: it offers the same WebKit build the local suite already runs.

## Files

The check is a vitest run of its own that drives real iPhones over WebDriver with `webdriverio`'s `remote()`. vitest gives the `describe`/`it` structure, the reporter, the timeouts and the exit code the rest of the repo already uses, and resolves the `shared/*` alias so the test seeds with the shared program item fixture and the real session key. The two WebdriverIO-based alternatives were tried and taken out again: `@wdio/browserstack-service` pins the stack to WebdriverIO 9, pulls in about 10 MB of gRPC, protobuf and Percy, writes a `log/` directory and reports to BrowserStack's observability product by default; the WebdriverIO test runner without the service worked but cost five `@wdio/*` packages, a second tsconfig for its global types and a `tsx` loader for the same `it` blocks vitest provides.

- **`vitest.config.ts`** — the standalone config: `tests/**/*.test.ts` under this directory, the global setup, 10 min test and 2 min hook timeouts, one test file at a time with `maxConcurrency: 8` so every scenario of every session can wait for its turn at once (a lower limit lets a waiting test hold a slot its predecessor needs), and the `shared` alias. Deliberately not a project of the root vitest config, so `yarn test` never spends device minutes.
- **`globalSetup.ts`** — once per run: loads `.env.browserstack` with `process.loadEnvFile`, checks that both local servers answer before any device minutes are spent, seeds the database once (the sessions share it), starts the `browserstack-local` tunnel with a per-run `localIdentifier`, hands the credentials, the identifier and test1's JWT to the test file through vitest's `provide`/`inject`, and stops the tunnel at the end.
- **`tests/safariResume.test.ts`** — the four scenarios as concurrent `it` blocks, run in **four sessions at once**: two per device, scenarios 2 and 3 in one and 4 and 1 in the other, so a full run takes as long as its slowest pair (about 4 minutes) rather than about 13 sequentially, and stays inside the account's 5 parallel sessions. A session opens lazily in its first scenario with `local: true` and the tunnel's identifier in `bstack:options`; its scenarios take turns in the order they start, since the tests themselves run concurrently and one phone can do one thing; the turn is taken when a test runs, so a `-t` filter or `.only` leaves no scenario waiting on one that never runs. Scenarios: Safari backgrounded 90 s; backgrounded 10 s (must not load on foregrounding, the next tick delivers); navigate away 90 s and back (the bfcache restore); screen off 90 s then wake and unlock, last in its session because the unlock is the least certain step. Each builds an outcome and concludes it: PASS passes, FAIL fails the `expect` on the verdict with the whole outcome in the diff, UNCLEAR skips the test with its reason. Each scenario resets its page afterwards, failures are collected per session, and `afterAll` sets each session's dashboard status through a `browserstack_executor` command and closes it. Device and scenario filters come from `BROWSERSTACK_DEVICE` and `BROWSERSTACK_SCENARIOS`; a session left with no scenario is not opened.
- **`utils/testServer.ts`** — the test server side: seeding once per run with the shared `twoPhaseProgramItem` fixture at `signupsOpenTime()`, a **probe** per session (its own added program item, so parallel sessions do not see each other's), and the local-server preflight. The test endpoint replaces the whole program, so every write posts the initial item plus every session's live probe, and writes are queued so a slower request cannot land after a newer one and drop another session's probe.
- **`utils/witness.ts`** — the in-page witness: GET requests to the settings endpoint (one per data load) and the `visibilitychange`/`pagehide`/`pageshow` events, recorded on the page and read back. Timing is measured on the phone's clock, since the device and the PC disagree by tens of seconds.
- **`utils/page.ts`** — the app page: booting it logged in, waiting for program items to appear or go, recovering a stale window handle, and resetting the page between scenarios.
- **`utils/device.ts`** — the phone: the `mobile:` commands BrowserStack allows (home, power, activate and query Safari) and the session's dashboard status.
- **`utils/verdict.ts`** — `observeAfter` and `resumeOutcome`: what a scenario saw, and the PASS/FAIL/UNCLEAR rules over it.
- **`frontServer.ts`** — serves `client/build` with an SPA fallback and proxies `/api` and `/auth` to the test server, so the phone sees one origin. Plain Node.
- **`buildFront.ts`** — the client build with that origin baked in as its API URL. Plain Node.
- **`utils/ports.ts`** — the ports, from the same per-worktree offset the dev servers use (`scripts/portOffset.ts`), imported relatively because the two plain-Node scripts resolve no aliases.
- **`.env.browserstack`** (gitignored and dockerignored, copy `.env.browserstack.sample`) — the account's username and access key. The username is the BrowserStack-generated one shown next to the key, not the login email.

**Dependencies.** `webdriverio` for the sessions and `browserstack-local` for the tunnel; vitest is the repo's. The `browserstack/` lint block allows the relative `../` imports these files need and registers the test's `conclude` and `inSession` helpers as assertions for `vitest/expect-expect`, since every scenario asserts through them.

## Running

The how-to, the expected result per scenario and the troubleshooting list are in [README.md](README.md); keep that current when the scripts change. In short: `yarn server:test`, `yarn browserstack:build`, `yarn browserstack:front`, then `yarn browserstack:test`, filtered with `BROWSERSTACK_DEVICE` and `BROWSERSTACK_SCENARIOS`.

Last full run 2026-11-01, iPhone 16 / iOS 18 and iPhone 14 / iOS 16: every scenario passed on both, and the vitest form of the test repeated all four on the iPhone 16 the same day. Lock, backgrounding and the bfcache restore all fire `visibilitychange`, the restore also fires `pagehide`/`pageshow` with `persisted: true`, and the resume refresh started within a few milliseconds of the page becoming visible with the item rendered in 0.1 to 0.8 s. The 10 s backgrounding produced no load and the regular tick delivered the item about 45 s later.

**In CI** `.github/workflows/browserstack.yml` runs it on pull requests that touch the page-resume client files, the shared helpers it imports or `browserstack/`, and on dispatch; see the README for triggers and secrets. The workflow builds and serves exactly as the local steps do (CI is a main checkout, so the ports are 5000 and 8000), and `BROWSERSTACK_BUILD` names each run's build on the dashboard. Its `paths` list is the resume code, what that code reads at runtime, and the check's own files, deliberately not everything the check could break on (test ids, the test endpoints, the shared types): those surface on the next run, and chasing them would turn the filter into most of the repository.

## What took finding out

- **Use `bs-local.com`, not `localhost` or `127.0.0.1`, in URLs the phone loads.** On iOS devices BrowserStack Local maps `bs-local.com` to the tunnel, while `localhost` and `127.0.0.1` are the phone itself. The page loads, so the API URL baked into the client bundle has to use the same host, which is why the build is a separate step rather than the dev server.
- **The dev server cannot be used.** Vite's `server.allowedHosts` blocks the `bs-local.com` host header, and the bundle's API URL would point at `127.0.0.1`.
- **The server cannot serve the build from a worktree under `.claude/`.** Its SPA fallback uses `res.sendFile` with an absolute path, and `send` refuses any path containing a dot-directory with a 404 that Express reports as a 500. `express.static` serving `/` is unaffected because it checks only the path below its root. Production paths have no dot-directories. `res.sendFile("index.html", { root: staticPath })` would fix it if worktrees become a regular workflow.
- **The API has to be proxied as the page's own origin.** The server's CORS allowlist is a fixed list and browsers send `Origin` on every POST, so a request from `bs-local.com:<port>` is refused with 403, which the client reports as "Unknown error". The front server strips `Origin` and `Referer` when proxying, making the request same-origin to the server.
- **BrowserStack's iOS Safari sessions allow only a subset of the Appium `mobile:` commands.** `lock`, `unlock` and `backgroundApp` are rejected. What works: `mobile: pressButton` with `home` to background Safari, `mobile: activateApp` with `com.apple.mobilesafari` to foreground it, `mobile: performIoHidEvent` with page `0x0C` usage `0x30` as the power button to turn the screen off and on, and `mobile: queryAppState` to confirm the state while away. After a wake, home then `activateApp` unlocked the passcode-free device on both iOS versions.
- **Compare timestamps on one clock.** The device clock was about 20 s off the PC's, enough to count a boot load as happening after an action. The harness takes `Date.now()` from the page for its `before` marker and reports the first load relative to the page's own visibility event.
- **Keep the in-page witness as JavaScript state.** Wrapping `window.fetch` and recording lifecycle events on `window` survives a lock, a backgrounding and a bfcache restore, and vanishes on a full reload, which is itself a result: it distinguishes a resume from a reload.
- **The app's own listener runs before the witness's**, so the resume load's request is on the wire a millisecond or so before the witness records the `visible` event; a small negative first-load offset is normal.
- **The seeding endpoints answer a plain `OK`**, not JSON.
- **iOS 16 Safari has answered every command with an error object after a navigation away and back** when that scenario followed the backgrounding ones: `getUrl` resolved to an object and the witness read came back without its arrays, and the next refresh failed. Switching to the current window handle after `back()` (and before each page reset) has kept the run going since; a result still carries `raw` when the witness shape is wrong, so the failure is visible rather than a crash.
- **BrowserStack ends a session after 90 s without a command**, and the screen-off and navigate-away scenarios are 90 s of silence. Run one at a time they stayed just under; with four sessions in flight they went over, and every later command answered `{"message":"Session not started or terminated"}`. The capabilities set `idleTimeout: 300`, BrowserStack's maximum, so an absence longer than about four and a half minutes needs a keep-alive command instead. The witness read used to take that error object for a reloaded page and report UNCLEAR; it now throws, because a broken session says nothing about the app.
- **The tunnel wrapper's log path is set on the instance directly.** On Windows `browserstack-local` wraps the path it builds in literal quotes, then fails to open that quoted name itself ("Could not clear log file: ENOENT") and passes the quotes on to the binary, which is launched with an argument array and needs none. The global setup assigns an unquoted path under the OS temp directory to the instance's `logfile` field before `start()`. The BrowserStack service constructs the tunnel itself and cannot be given this fix, which is one more reason it is not used.

## Android

There is no Android spec, by decision. Chrome on Android is the Chromium the Playwright "Mobile Chrome" project already runs, with the same documented page lifecycle (`visibilitychange` on backgrounding and screen off, background timers throttled to once a minute and the page frozen after about five minutes, `pageshow` with `persisted: true` on a bfcache restore), so the Playwright spec already pins the app's side of that contract and the remaining risk is the throttling and freezing interacting with the poll timer, which the resume age check covers by design. The Safari check exists because none of that holds for WebKit. Adding Android to the spec would mean a Chrome variant of the device actions (Chrome's package name, `mobile: pressKey` for home, whatever lock commands BrowserStack allows on Android) and a second device list; the harness and verdicts would carry over. Until a manual check surprises someone, the manual procedure in [README.md](README.md) (USB remote debugging with port forwarding, the data loads watched in the Network panel) is the Android check.
